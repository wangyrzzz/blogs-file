# 3 种常用的缓存读写策略详解

缓存设计的难点不在于把数据放进 Redis，而在于回答三个问题：数据从哪里读、数据更新时谁负责同步、缓存与数据库不一致时系统能接受到什么程度。常见的缓存读写策略可以归纳为 Cache Aside、Read/Write Through 和 Write Behind。

这三种模式没有绝对的优劣。选择时应结合读写比例、数据一致性要求、缓存服务能力和故障恢复成本，而不是只看一次请求的延迟。

## 一、Cache Aside：旁路缓存

Cache Aside 是业务系统中最常用的模式。应用同时面对缓存和数据库，缓存不是唯一数据源。

### 读流程

1. 应用查询缓存；
2. 命中则直接返回；
3. 未命中则查询数据库；
4. 查询成功后回填缓存并返回。

```java
String value = cache.get(key);
if (value == null) {
    value = repository.find(id);
    if (value != null) {
        cache.set(key, value, randomTtl());
    }
}
return value;
```

回填时要考虑缓存击穿、空值缓存和并发请求。对热点 Key 可以使用互斥锁、逻辑过期或请求合并；对不存在的数据短暂缓存空值，避免恶意或错误请求持续打穿数据库。

### 写流程

常见顺序是“先更新数据库，再删除缓存”：

```text
更新 DB 成功 -> 删除 Cache -> 返回成功
```

之所以不先删缓存，是因为“先删缓存、后更新数据库”可能出现以下时序：读请求发现缓存为空，读取旧数据并回填；写请求随后才提交新数据，最终缓存又被旧值覆盖。

“先更新数据库、后删除缓存”也不是绝对强一致。读请求可能在数据库更新前读到旧值，写请求更新数据库并删除缓存后，读请求再把旧值回填。因此对强一致场景还需要串行化、延迟双删、订阅数据库变更日志或改用更严格的架构。

### 为什么通常删除而不是更新缓存

- 业务更新可能只修改对象的一部分，重新组装完整缓存容易遗漏字段；
- 删除操作简单，下一次读取时再按数据库重建；
- 避免多个并发写请求按不同顺序更新缓存。

缓存删除失败必须有补偿机制，例如重试队列、可靠消息或定期校验。不要把“删除缓存”当成不可能失败的本地操作。

## 二、Read/Write Through：读写穿透

在这种模式下，应用只访问缓存层，由缓存层负责从数据库加载和持久化。

### Read Through

缓存未命中时，由缓存组件自动查询数据库并回填，应用无需编写回填逻辑。

### Write Through

写请求先到缓存层，再由缓存层同步写数据库。只有缓存和数据库都成功时才返回成功。

这种模式对应用透明，但 Redis 本身不会自动替业务把对象写入 MySQL，通常需要缓存代理、ORM 扩展或专门的数据访问层实现。因此它在通用 Web 项目中没有 Cache Aside 常见。

它的优点是读写逻辑集中、数据访问方更简单；缺点是中间层复杂、失败处理困难，并且写入延迟受数据库影响。

## 三、Write Behind：异步写回

Write Behind 先更新缓存并立即返回，之后由后台任务批量写入数据库：

```text
应用写 Cache -> 写入队列 -> 合并/批量刷 DB
```

它适合高频计数、临时状态和允许短暂延迟落库的场景，例如浏览量、点赞数、设备遥测聚合。优点是吞吐高、可以合并多次更新；缺点是缓存或队列故障时可能丢失尚未持久化的数据。

因此库存、余额、支付结果等强一致数据不应只依赖 Write Behind。使用该模式时至少要设计持久化队列、重试、死信、刷写监控和恢复补偿。

## 四、三种模式对比

| 模式 | 读写责任 | 一致性 | 适用场景 | 主要风险 |
| --- | --- | --- | --- | --- |
| Cache Aside | 应用负责缓存与数据库 | 通常是最终一致 | 读多写少、缓存可重建 | 旁路逻辑分散、并发不一致 |
| Read/Write Through | 缓存层负责同步 | 可做到较强一致 | 访问层统一、缓存代理完善 | 中间层复杂、写延迟较高 |
| Write Behind | 缓存先写，异步落库 | 最终一致 | 高频写、可容忍延迟 | 宕机丢数据、恢复复杂 |

## 五、落地时还要考虑的细节

### TTL 与随机过期

为缓存设置 TTL，避免永久脏数据和内存无限增长。大量 Key 使用同一个过期时间可能造成缓存雪崩，可以加入随机偏移，并对热点数据做预热和限流。

### 缓存穿透、击穿与雪崩

- 穿透：请求不存在的数据，可缓存空值或使用布隆过滤器；
- 击穿：热点 Key 同时失效，可使用互斥锁或逻辑过期；
- 雪崩：大量 Key 同时失效或缓存集群不可用，需要限流、降级和多级缓存。

### 失效与降级

缓存不可用时，系统应明确是降级读数据库、返回兜底数据还是快速失败。降级必须有数据库连接和并发保护，否则 Redis 故障会把数据库一起压垮。

## 总结

Cache Aside 是大多数业务的起点；Read/Write Through 适合把数据访问能力下沉到统一中间层；Write Behind 适合高吞吐、可异步持久化的场景。无论采用哪种模式，都需要明确一致性边界、失败补偿、过期策略和降级方案。
