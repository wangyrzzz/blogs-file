# Dubbo 3 探索：服务调用、注册发现与治理

Dubbo 3 是面向微服务场景的 RPC 框架，核心仍然是“服务提供者暴露接口，消费者通过代理发起调用，注册中心负责发现地址”。与单体应用中的本地方法调用相比，RPC 调用必须把网络延迟、序列化、超时、重试和服务不可用纳入设计。

## 一、一次 RPC 调用发生了什么

消费者启动时订阅服务元数据和实例地址，框架为接口创建代理。调用代理时，客户端根据路由和负载均衡规则选择一个提供者，完成序列化、网络传输、反序列化，再把结果或异常返回给业务代码。

```text
Consumer Proxy
     |
     v
路由/负载均衡 -> 连接池 -> 序列化 -> 网络
                                      |
                                      v
                              Provider Skeleton
```

注册中心只负责发现和变更通知，不应被当成每次请求的中转站。RPC 数据流通常是消费者直连提供者。

## 二、定义稳定的服务接口

接口应以业务能力为边界，而不是简单暴露数据库表的 CRUD。参数和返回对象应使用明确的 DTO，避免把内部实体直接暴露给远程调用方。

```java
public interface OrderService {
    OrderResult create(CreateOrderCommand command);
    OrderResult findById(Long orderId);
}
```

远程接口要考虑兼容演进：新增字段通常应允许旧客户端忽略；删除字段要经过兼容窗口；枚举新增值不能让旧客户端直接反序列化失败。对高风险操作，应把幂等键作为显式参数。

## 三、注册中心与服务发现

注册中心可以使用 Nacos、ZooKeeper、可观测的 Kubernetes 服务发现等方案。选型时关注一致性模型、健康检查、网络分区行为和运维能力。服务实例注册的信息至少应包括应用名、协议、端口、版本、分组和元数据。

在 Kubernetes 中，也可以直接使用 Service DNS，让服务通过 `order-service.default.svc.cluster.local` 访问。此时要明确是使用 Dubbo 注册中心能力，还是使用 Kubernetes 原生服务发现，避免两套地址来源互相覆盖。

## 四、Dubbo 3 协议选择

Dubbo 3 支持多种通信协议。传统 Dubbo 协议在 Java 生态中成熟；Triple 基于 HTTP/2 和 gRPC 生态，便于异构语言互通。协议选择应结合已有客户端、网关、代理、序列化和运维能力，而不是只看协议名称。

使用 Triple 或其他跨语言协议时，要优先确定 IDL、字段兼容规则和错误码约定。Java 服务之间能调用，并不代表 Go、Node.js 或 Python 客户端能够正确理解同一套异常和枚举。

## 五、超时、重试与幂等

远程调用的超时必须小于上游请求的剩余时间，避免线程层层堆积。重试只能用于明确可重试的失败，例如连接建立失败或临时不可用；创建订单、扣库存等写操作如果没有幂等键，自动重试可能造成重复业务。

```text
上游超时 2s
  -> 服务 A 调用服务 B 最多 1.5s
     -> 服务 B 调用服务 C 最多 800ms
```

重试次数、退避时间和最大总耗时应统一配置并纳入监控。不要在每一层都配置“3 次重试”，否则一次请求可能被放大几十倍。

## 六、版本、分组与灰度

服务版本、分组和标签可以用于隔离不同环境或灰度流量。灰度路由应以稳定的用户、租户或请求标识计算，保证同一用户在一段时间内命中同一版本。发布期间要同时考虑接口兼容、序列化兼容和数据结构兼容。

## 七、治理与可观测性

生产环境至少应监控 QPS、P99 延迟、超时率、异常率、连接数、线程池队列和实例变更。每次调用应记录 TraceId、接口名、版本、耗时和结果码，但不要默认打印完整请求参数，尤其是密码、Token 和个人敏感信息。

## 八、排查调用失败

建议按顺序排查：

1. 消费者是否订阅到正确的服务名、分组和版本；
2. 提供者是否注册了可访问的地址和端口；
3. DNS、网络策略、防火墙和容器端口是否连通；
4. 序列化协议、接口签名和字段版本是否兼容；
5. 是否存在超时、线程池耗尽、重试放大或下游依赖阻塞。

不要只根据“服务已注册”判断调用链路正常，注册成功与业务端口可达是两个独立条件。

## 总结

Dubbo 3 的价值不仅在于把本地方法变成远程调用，更在于提供注册、路由、负载均衡和治理能力。接口契约、超时重试、幂等和可观测性设计得越清楚，框架配置越简单，线上故障也越容易定位。
