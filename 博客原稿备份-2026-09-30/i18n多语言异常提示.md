# i18n 多语言异常提示设计

多语言异常提示的目标不是把每条中文字符串翻译成英文，而是让异常具备稳定的错误码、可替换的消息模板和明确的 Locale 来源。前端、日志和监控也应围绕错误码工作，而不是依赖某一种语言的文本。

## 一、错误码与展示消息分离

建议异常至少包含 `code`、消息参数和可选原因：

```java
public class BizException extends RuntimeException {
    private final String code;
    private final Object[] args;

    public BizException(String code, Object... args) {
        this.code = code;
        this.args = args;
    }
}
```

业务代码抛出 `order.notFound`，而不是直接抛出“订单不存在”。错误码用于前端分支、国际化资源、日志聚合和自动化测试；展示文本由当前请求的语言决定。

## 二、Spring MessageSource

在 Spring Boot 中，可以准备 `messages_zh_CN.properties` 和 `messages_en_US.properties`：

```properties
# messages_zh_CN.properties
order.notFound=订单 {0} 不存在
stock.insufficient=商品 {0} 库存不足
```

```properties
# messages_en_US.properties
order.notFound=Order {0} was not found
stock.insufficient=Insufficient stock for item {0}
```

通过 `MessageSource` 根据错误码和参数解析消息：

```java
String message = messageSource.getMessage(
        exception.getCode(),
        exception.getArgs(),
        locale);
```

资源文件的编码、默认语言、缓存时间和不存在 key 的处理方式应在部署环境中明确配置。缺少翻译时可以回退到默认 Locale，但不应把异常堆栈返回给用户。

## 三、Locale 从哪里来

常见来源包括 `Accept-Language` 请求头、用户账号偏好和租户配置。优先级需要统一，否则同一用户在不同接口看到的语言会不一致。对后台任务和消息消费，没有 HTTP 请求头，应在任务元数据中保存 Locale，或使用系统默认语言。

`Accept-Language` 是客户端偏好，不是可信身份信息。它只影响展示语言，不能用于权限、金额格式的安全判断或租户选择。

## 四、统一异常处理

返回结构建议包含稳定的错误码和本地化消息：

```json
{
  "code": "order.notFound",
  "message": "订单 10001 不存在",
  "traceId": "8b1f..."
}
```

全局异常处理器负责把已知业务异常转换为业务错误，把未知异常记录完整堆栈并返回通用提示。日志应使用服务默认语言或结构化字段，不能因为请求语言不同而让监控规则失效。

## 五、参数和敏感信息

消息参数应是安全、可展示的业务值，例如订单号或商品名称。不要把密码、Token、完整手机号、数据库异常和 SQL 直接插入提示。模板参数数量变化时要补充测试，避免运行时出现格式化异常。

## 六、前后端如何协作

前端如果拥有完整的语言包，可以只使用 `code` 自行翻译；如果由后端翻译，则应保证所有端的 Locale 约定一致。不要让前端根据 `message.includes("库存不足")` 判断业务逻辑，这会被语言切换直接破坏。

对于校验错误，可以返回字段级错误：

```json
{
  "code": "validation.failed",
  "fields": [
    {"field": "email", "code": "email.invalid", "message": "邮箱格式不正确"}
  ]
}
```

## 七、测试清单

- 中文、英文和未支持 Locale 的回退结果；
- 参数缺失、参数包含特殊字符时的输出；
- 异步任务没有请求上下文时的语言；
- 异常日志是否保留错误码和 TraceId；
- 翻译文件缺少 key 时是否能被构建或测试发现。

## 总结

多语言异常提示的稳定边界是“错误码负责机器识别，Locale 决定展示文本，日志保留完整上下文”。先建立统一异常模型，再接入 MessageSource 或前端语言包，后续增加语言时就不需要改动业务判断代码。
