# 分库分表实战：从拆分动机到稳定落地

当单库单表的容量、连接数或写入吞吐达到瓶颈时，分库分表可以把压力分散到多个数据库实例和数据表中。但它不是“把表名拼接一下”这么简单：拆分之后，事务、分页、唯一约束、扩容和数据迁移都需要重新设计。

## 一、什么时候需要分库分表

分库分表主要解决三类问题：

- 单表数据量过大，索引变长，查询和维护成本明显上升；
- 单库连接数、磁盘 I/O 或写入吞吐达到上限；
- 热点业务集中在少数表或少数租户，需要隔离故障域。

在真正拆分前，应先确认瓶颈是否可以通过索引优化、归档历史数据、读写分离或增加缓存解决。分片会增加系统复杂度，不能把它当成数据库优化的第一选择。

## 二、两种常见拆分方式

### 垂直拆分

垂直分库按业务边界拆分，例如把用户、订单、库存分别放到不同数据库；垂直分表按字段冷热拆分，例如把订单主表中的大文本、扩展 JSON 放到详情表。

垂直拆分的优点是边界清晰、单个服务更容易独立扩展。缺点是跨库事务和跨库查询增加了，拆分前必须梳理业务调用链。

### 水平拆分

水平分库或分表保留相同的表结构，只把不同数据行分散到多个节点。例如按 `user_id` 对订单表进行分片：

```text
order_0000 = hash(user_id) % 4 == 0
order_0001 = hash(user_id) % 4 == 1
order_0002 = hash(user_id) % 4 == 2
order_0003 = hash(user_id) % 4 == 3
```

水平拆分的关键是选择稳定、分布均匀并且查询时经常携带的分片键。若最常见的查询条件是 `tenant_id`，却按自增主键分片，查询很可能退化成全分片扫描。

## 三、分片键怎么选

可以用下面几个问题筛选候选字段：

1. 查询条件中是否经常出现？
2. 取值是否足够均匀，能否避免热点分片？
3. 业务关系是否以它为边界，例如租户、用户或店铺？
4. 是否稳定，是否会发生迁移？
5. 能否在新增记录时直接得到？

通常不建议选择会频繁修改的字段，也不建议只按时间分片而没有冷热归档策略。时间分片写入简单，但当前月份可能成为热点；哈希分片分布均匀，却不利于按时间范围查询。实际项目常采用“业务键哈希 + 时间归档”或“租户隔离 + 租户内分表”的组合方案。

## 四、主键与唯一性

拆分后，数据库自增 ID 只能保证单表内唯一，不能保证全局唯一。常用方案包括号段模式、Snowflake、数据库发号器和 UUID。选择时应关注有序性、长度、时钟回拨、服务重启和多机并发。

原来数据库上的唯一索引也要重新审视。例如原来的 `UNIQUE(order_no)` 拆分后只在单表生效，必须改成业务侧生成全局唯一订单号，或者把唯一性校验下沉到一个集中服务。

## 五、跨分片查询与分页

带分片键的查询可以路由到单个分片，是最理想的情况：

```sql
SELECT id, user_id, status, created_at
FROM orders
WHERE user_id = ? AND status = ?
ORDER BY id DESC
LIMIT 20;
```

不带分片键的查询会产生广播查询，需要在各分片执行后合并结果。跨分片排序、聚合和深分页都会放大成本，因此应尽量：

- 在接口中要求或推导出分片键；
- 使用基于游标的分页，例如 `id < last_id`，减少 `OFFSET`；
- 把全局统计放到汇总表或数仓中，不要每次实时扫所有分片；
- 对广播查询设置超时、并发度和最大返回量。

## 六、事务与一致性

单分片事务仍然可以使用本地事务；跨分片写入则不应默认依赖本地事务注解。可以按业务重要性选择：

- 把强一致操作重新设计为单分片内完成；
- 使用本地消息表或 Outbox，把后续动作异步化；
- 需要跨服务协调时使用可靠消息、Saga 或 TCC；
- 只在确有必要时使用 XA，并评估锁持有时间和吞吐损失。

分布式事务框架不能替代幂等设计。每个消费动作都应有业务唯一键，重复投递时能够安全地返回已有结果。

## 七、以 ShardingSphere 为例的配置思路

不同版本的配置键可能不同，下面只展示核心结构：

```yaml
spring:
  shardingsphere:
    datasource:
      names: ds0,ds1
    rules:
      sharding:
        tables:
          orders:
            actual-data-nodes: ds$->{0..1}.orders_$->{0..3}
            database-strategy:
              standard:
                sharding-column: user_id
                sharding-algorithm-name: db-inline
            table-strategy:
              standard:
                sharding-column: user_id
                sharding-algorithm-name: table-inline
```

上线前必须用真实 SQL 验证路由结果，尤其关注隐式类型转换、范围条件、排序、分页和批量写入。不要只验证“能启动”。

## 八、扩容与迁移

从四个分片扩到八个分片时，直接修改取模规则会导致同一条数据被路由到不同位置。更稳妥的做法是：

1. 设计可版本化的路由规则，或采用一致性哈希、号段路由；
2. 先建立新分片并做全量迁移；
3. 通过 CDC、双写或增量日志追平变更；
4. 校验行数、校验和、抽样业务结果；
5. 灰度切换读流量，再切换写流量；
6. 保留回滚窗口，确认稳定后再清理旧数据。

## 总结

分库分表的核心不是拆得越多越好，而是让常见请求尽量落在单分片内，并让数据边界、唯一性和扩容路径可解释、可验证。先明确瓶颈和业务分片键，再围绕事务、查询、迁移和运维成本做整体设计，才能避免“数据库拆开了，问题反而分散到每个业务接口里”。
