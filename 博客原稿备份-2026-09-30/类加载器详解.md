# 类加载器详解

Java 类加载器负责把类的二进制字节流加载到 JVM，并生成对应的 `Class` 对象。它不仅决定类从哪里来，也决定同名类是否被视为同一个类型，因此和插件隔离、容器部署、SPI、热加载以及常见的类冲突问题都有关系。

## 一、类加载过程

一个类从字节码到可使用，大致经历加载、连接和初始化：

1. 加载：根据全限定类名找到字节流，在方法区或元空间形成运行时结构，并创建 `Class` 对象；
2. 连接：包括验证、准备和解析；
3. 初始化：执行类变量赋值和静态代码块。

类不一定在 JVM 启动时全部加载，而是通常在首次主动使用时按需加载。调用 `new`、访问静态字段、调用静态方法、反射加载等行为都可能触发初始化；仅仅通过某些方式获取 `Class` 对象不一定会执行静态初始化。

## 二、ClassLoader 的职责

`ClassLoader` 的职责是找到字节码并定义类。一个类的身份由“全限定类名 + 定义它的类加载器”共同决定：

```java
Class<?> c1 = loader1.loadClass("com.example.Plugin");
Class<?> c2 = loader2.loadClass("com.example.Plugin");
System.out.println(c1 == c2); // 可能为 false
```

即使两个类文件内容相同，只要由不同加载器定义，类型转换也可能失败。这就是很多容器隔离和 `ClassCastException` 的根源。

## 三、JDK 内置加载器

JDK 8 常见的层次包括启动类加载器、扩展类加载器和应用类加载器。JDK 9 引入模块系统后，扩展类加载器对应为平台类加载器，`rt.jar` 的描述也不再适用于模块化 JDK。

- 启动类加载器由 JVM 实现，负责核心模块，Java 层通常显示为 `null`；
- 平台类加载器负责部分 Java 平台模块；
- 应用类加载器负责应用 classpath 或 module path 上的类；
- 用户还可以实现自定义类加载器。

查看当前类的加载器：

```java
System.out.println(MyApp.class.getClassLoader());
System.out.println(String.class.getClassLoader()); // 通常为 null
System.out.println(Thread.currentThread().getContextClassLoader());
```

不同 JDK 版本、启动参数和容器实现可能输出不同的具体类名，不应把某个 JDK 8 的类名硬编码为通用结论。

## 四、双亲委派模型

当一个类加载器收到加载请求时，通常按以下顺序工作：

1. 先检查自己是否已经加载过该类；
2. 有父加载器则把请求委派给父加载器；
3. 父加载器无法找到时，当前加载器再尝试加载；
4. 最终找不到则抛出 `ClassNotFoundException`。

这种模型的价值主要有两点：避免同一加载器重复加载，以及让核心类优先由更高层加载器定义。应用代码即使放置了一个名为 `java.lang.String` 的类，也不能随意替换 JDK 核心类。

需要注意，双亲委派是 `ClassLoader` 的常见实现策略，不是所有场景都必须严格遵守。Tomcat、OSGi 和一些插件系统会根据隔离需求采用不同的委派顺序。

## 五、自定义类加载器

如果希望保留双亲委派，通常重写 `findClass`：

```java
public class DirectoryClassLoader extends ClassLoader {
    private final Path root;

    public DirectoryClassLoader(Path root, ClassLoader parent) {
        super(parent);
        this.root = root;
    }

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        Path path = root.resolve(name.replace('.', '/') + ".class");
        try {
            byte[] bytes = Files.readAllBytes(path);
            return defineClass(name, bytes, 0, bytes.length);
        } catch (IOException e) {
            throw new ClassNotFoundException(name, e);
        }
    }
}
```

只有明确需要改变加载顺序时才重写 `loadClass`。自定义加载器还必须处理资源加载、并发加载、生命周期和关闭文件句柄，否则可能造成类卸载失败或 Metaspace 增长。

## 六、线程上下文类加载器与 SPI

双亲委派天然适合“父加载器使用父路径中的类”，但 SPI 的接口可能由高层加载器加载，实现类却位于应用 classpath。线程上下文类加载器允许框架通过当前线程获取应用侧的实现，常见于 JDBC、JNDI、日志和容器场景。

```java
ClassLoader loader = Thread.currentThread().getContextClassLoader();
ServiceLoader<MyPlugin> plugins = ServiceLoader.load(MyPlugin.class, loader);
```

使用完自定义上下文类加载器后，应恢复原值，尤其是在共享线程池中，否则可能让后续任务错误加载另一套插件。

## 七、常见问题

### ClassNotFoundException 与 NoClassDefFoundError

`ClassNotFoundException` 常表示显式加载时找不到类；`NoClassDefFoundError` 常表示类在编译期存在，但运行时定义或初始化依赖失败。排查时要同时看根因、依赖树、加载器层次和运行时 classpath。

### Jar 包冲突

同一个类由不同版本 Jar 提供时，可能出现方法不存在、类型不兼容或初始化失败。应从依赖树、容器共享目录、插件目录和启动参数确认最终加载来源，而不是只看源码中的依赖声明。

### 类加载器泄漏

Web 应用反复发布后，如果线程、定时任务、静态缓存、JDBC 驱动或日志框架仍持有旧加载器，旧类无法回收，最终可能出现 Metaspace OOM。应用停止时应取消任务、关闭线程池和释放资源。

## 总结

类加载器决定类的来源、身份和隔离边界。理解加载生命周期、双亲委派、线程上下文类加载器和自定义加载器，就能更准确地解释插件加载失败、容器类冲突和 SPI 找不到实现等问题。
